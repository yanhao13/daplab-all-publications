perf optimization methodology :measurement: what is perf? basic metric is exec time t(for a single op called latency), derived matric including thruput(#op/t or #programs/t) and flops(#floating pt op/t), <br>
	• speedup: speedup of B wrt A tA/tB, parallel speedup tserial/tparallel, slowdown is inverse of speedup<br>
	• scalability: scaling efficiency E=tserial/{tparallel*p} <= 1 p is #processes/threads, strong scaling i.e. constant problem size while increasing p defi that measures how well a sys performs a fixed problem size as #resources like processor gpu increases, goal to reduce time to solve the same problem by adding more computational resources, how the solution time varies with #processors for a fixed total problem size, increasing sync cost but fixed amount of work, weak scaling i.e. increasing problem size proportional to p defi that measures how well a sys performs as both wkload size and #resources increase proportionally, goal to keep the runtime constant as the wkload grows in tandem with the resources, weak scaling is defined as how the solution time varies with #processors for a fixed problem size per processor, work per process is constant, increasing sync cost increasing work -> while speedup tells us how much faster becomes, scalability tells us how well that speedup holds as we continue adding resources, scaling efficiency measures how closer we are to ideal linear scaling<br>
	• characteristics of a good perf metric: a good perf metric must have attributes including linear reliable repeatable easy2use consistent independent, time-based mean like sec should be directly proportional to total weighted time if time doubles mean value double, rate-based mean like thruput op per sec should be inversely proportional to the total weighted time if time doubles mean value reduced by half, which mean satisfies these criteria? computing averages using mean values including average exec time using arithmetic mean 1/n\sum_i=1^n{ti}, average perf/thruput if t is held constant then use arithmetic mean if #op is held constant then use harmonic mean=n/{\sum_i=1^n{ti/#op}}, average speedup slowdown ot any ration using geometric mean=\sqrt^n{\pi_i=1^n{speedupi}}, arithmetic mean that produces a value that is directly proportional to the total time, when sum of raw values has physical meaning, use for summarizing times not rates, use when measuring values that contributes equally to the final result such as in time measurements or perf in identical wkloads, harmonic mean that produces a mean value that is proportional to sum of the inverse of times, use for averaging rates like thruput/speed not times where the individual measurements are inversely related to the total perf, like f1 score in ml is harmonic mean of precision and recall, like network thruput is often used when measuring average thruput across multiple links, geometric mean that used when numbers in the series are not independent or if numbers tend to make large fluctuations, used when comparing ratios or proportions like growth rates or perf scaling across sys, used when data pts have different units or scales, like benchmark perf across a variety of wkloads, like financial sys to calculate average investment returns<br>
	• benchmarking wkloads :in ascending order of complexity: micro kernels that test a specific processor feature like fp/l1cache/l2cache, micro benchmark that small program from a programming assignment like merge sort in isolation, kernels that a specific algorithm in a real program like quicksort/binary search/dgemm dense generalized matrix multiplication, synthetic benchmark that try to reproduce wkload of a class of applications like dhrystone concentrates on string handling and linpack solves a dense sys of linear equations, real applications that a real application used for a specific purpose like word/mysql/namd molecular dynamics/mlperf inference benchmark, real wkflows that a set of applications working together like candle wkflow for ml applied to cancer research<br>
	• measuring and reporting perf including reproducibility and accuracy, former is always include absolute exec time, report relevant hwsw info of cpu mem network disk experimental config code pseudo code compiler ver compilation flags lib ver os ver, latter is repetitions of 5/10/100 depends on variability, if high variability results then try to understand why and reduce it, include stddev variance maxmin interquartile range, use boxplot for chart representations<br>
	• basic and advanced measurement techniques: basic is time measurement, application thruput, breakdown phases/iterations, advanced is profiling, tracing<br>
	• time defi: real time/wallclock/elapsed that actual elapsed time from a pt in the past, cpu time/process that spent executing cpu instr including user time and system time, non-cpu time that spent waiting i.e. idle cpu for io, virtualization, measuring time in linux/c/python/pytorch<br>
	• profiling including sampling and counting: former is sample applications during exec to infer a statistical distribution like approximate time spent in each instr of the code, latter is count exact events, sw counters(implemented in kernel) that count specific events like count number of mem allocations malloc(), hw perf counters that counters maintained in reg like count number of l2 misses, fp op, #branch mispredictions<br>
	• tracing: explicit code instrumentation with tracing primitives, higher overhead than profiling, linux perf tracing can be applied to any code of applications runtime kernel, tracing utilities including strace(trace sys calls made by an application), ftrace(trace exec flow of kernel func)<br><br>

perf optimization methodology :analysis: amdahl's law S(p,s)=1/{1-p+p/s} S is speedup of the entire application(or runtime,os,etc), p is portion of the exec time spent in the code section bf improvement(if time for p is high the section is called critical section), s is speedup of the improved code section, overall speedup is limited by how much time the improved code takes compared to the rest, <br>
	- perf analysis step: first identify critical path i.e. the section of the program that counts for most of the time(high value of amdahl's p) that critical path characteristics is very slow to execute(high latency) and/or executed many times, use output of perf measurement step(profiling,tracing,etc), verify hypothesis of critical path that comment code and and run again, second identify the bottleneck i.e. the sys resource that affects that exec time of the critical path, that need to understand hwsw architecture, bottleneck type of data mvment vs computation<br>
	- data mvment and packet size: true for any data mvment of network, poie, dram, here small packets that low latency becomes very important for perf and full bdwidth is not reached, large packets that high bdwidth becomes very important for perf and latency is not relevant, data mvment locality principle :latency: latency in cpu cycles assuming a 2.0ghz cpu is more locality with small granularity low latency high bdwidth, less locality with large granularity high latency low bdwidth, latency values over the yrs a cool tool<br>
	- bottleneck categories: bottleneck corresponds to specific hw limits, perf analysis problem is how far is perf from hw limits?<br>
	- perf models objectives: identify perf bottlenecks, determines hw limits to optimization including determines how fare we are from hw limits and motivate algorithmic changes, project perf on future hw or applications<br>
	- peak flops: depend on compute unit architecture of cpu gpu tpu fpga, #cores and #threads, clock freq, precision of dp(64bit) sp(32bit) hp(16bit), simd instr in the cores of intel avx ibm altivec, cpu formula for peak flops #tot_cores*cycles/sec*flops/cycles<br>
	- roofline perf model: thruput based model, developed at doe lawrence berkeley labs, metrics including peak flops, mem bdwidth (data/time)[bytes/sec], arithmetic intensity program property (#arithmetic ops/dram data)[flop/bytes] i.e. bytes as seen from dram, note flop!=flops, here arithmetic intensity is the ratio bt #executed op and #bytes transferred bt cpu and mem, smaller arithmetic intensity means a larger pressure on the mem subsystem and conversely larger arithmetic intensity means a larger pressure on the cpu computational resources, naïve roofline perf model that assumptions considers dram and processor, actual flops are limited first by dram bdwidth(mem-bound) and then by cpu/gpu peak flops(compute-bound), actual measured perf is below the roofline, depending on arithmetic intensity including mem-bound code and compute-bound code, log-log scale is used for clarity, more complex roofline perf model that assumptions considers also caches, considered a basic dram-only roofline model that bytes as seen from dram access
